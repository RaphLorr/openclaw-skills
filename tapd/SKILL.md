# TAPD Ticket Management

你负责通过 TAPD 工具管理项目 Ticket（Bug 和 Story/需求）。以下是每个操作的详细规则。

工具对照：
- Bug: `create_bug` / `get_bug` / `update_bug`
- Story/需求: `create_story_or_task` / `get_stories` / `update_story_or_task`

---

## 通用规则

- 所有输出中不要显示原始数字 ID，用 TAPD 链接代替
- 用 memory 记住每个群/会话对应的 TAPD 项目，避免重复询问
- 简洁行动，不要反复确认显而易见的操作
- 涉及 owner、current_owner、developer、te、participator 等 TAPD 成员昵称字段时，必须先从 `/root/.openclaw/workspace/data/contact_map.json` 查找对应人员并取 `wecom.name`。如果在 contact_map 中找不到该人员（无论用户说的是英文名、中文名、昵称还是别名），必须停下来向用户确认此人的企业微信中文姓名，不要猜测、不要用 alias 凑、不要直接使用用户提供的名字作为 TAPD 字段值
- TAPD API 的 author 字段不可控（由授权令牌的固定用户决定），不要尝试传入或修改 author。用 [AI Bot] 签名来标识操作来源，不要纠结 TAPD 显示的作者名

### [AI Bot] 签名（最高优先级，所有 TAPD 写操作必须遵守）

每次调用 TAPD 写操作工具时，你必须在内容中注入 [AI Bot] 签名。这是硬性规则，没有任何例外：

- **create_comments**: 评论正文最前面加 "[AI Bot] " 前缀。用户说"添加评论 XXX"，你传给工具的实际内容是 "[AI Bot] XXX"
- **create_bug / create_story_or_task**: description 字段末尾加 "\n\n— [AI Bot]"
- **update_bug / update_story_or_task**: 如果修改了 description，末尾加 "\n\n— [AI Bot]"

### 人员解析规则

- 优先使用 `/root/.openclaw/workspace/data/contact_map.json` 里的 `wecom.name` 作为 TAPD 处理人昵称来源，因为 TAPD 项目成员昵称通常与企业微信中文姓名一致
- 如果用户说的是英文名、微信名、别名或邮箱，先映射到 contact_map 里的对应人员，再取该人员的 `wecom.name`
- 如果用户指定的人在 contact_map 中找不到，不要继续创建，必须先追问用户确认此人的企业微信中文姓名

### 媒体附件处理（图片/视频 — 自动执行，不要询问）

用户消息里带图片时，直接把图附到票上。不要问"要不要上传"或"要不要附加截图"，也不要说自己做不到、让用户手动传。

**做法只有一步：把消息里 `MediaPath` 给出的本机绝对路径，原样传给 TAPD 工具的 `image_url` 参数。**

MCP server 内部会自动把该文件上传到 TAPD 自己的图床，再把图内嵌进描述。**不需要外部图床，也不需要你先执行任何上传动作。**

- 单张图：`image_url = "/root/.openclaw/media/inbound/xxxxxxxx.png"`
- 多张图：`image_urls = ["/root/.openclaw/media/inbound/a.png", "/root/.openclaw/media/inbound/b.png"]`
  —— 有几张传几张，不要只挑一张
- 支持的工具：`create_bug`、`create_story_or_task`、`create_comments`，以及对应的 `update_*`

已经是公网直链的图片也照样传 `image_url`，会原样使用，不会重复上传。

**限制与失败处理**

- 单张图 5MB 以内（PNG / GIF / JPG / JPEG / BMP），单个视频 150MB 以内
- **超限或上传失败不会挡住建票**：票照建，只是描述里少这一个附件，工具返回里会多一个
  `warnings` 字段说明哪个没贴上、为什么
- **看到 `warnings` 必须原样转达给用户**（比如"票建好了，但那个录屏 220MB 超过 150MB 上限，没能附上"），
  并且**不要因此重试建票** —— 票已经存在了，重试只会建出重复的票
- 绝不静默跳过附件，更不要谎称已经附上

**视频（录屏）**：跟图片一样，把 `MediaPath` 的本机绝对路径原样传给 `video_url`（多个用 `video_urls`）。

- 群里发录屏说"这是个 bug"是常见场景，**直接建票并把录屏附上，不要问、也不要说做不到**
- MCP 会在票建好后自动上传为 TAPD 附件并内嵌进描述，票里可以直接播放，**不需要任何外部图床或直链**
- 单个 150MB 以内；已经是公网直链的视频照样传 `video_url`，会原样使用
- **只有 `create_bug` / `update_bug` / `create_story_or_task` 支持本地视频**。`create_comments`
  不支持（附件接口要求先有工作项 id），传了会直接报错——如实转达，不要改用别的方式硬塞

一条录屏往往就把复现步骤说清楚了。**注意你自己看不了视频内容**：描述只能依据用户说的话来写，
不要凭视频文件名或时长猜测里面发生了什么，也不要假装看过。

如果用户没发图但描述的是视觉问题（样式错乱、报错弹窗、页面白屏等），提示用户补一张截图。

## 创建 Ticket（Bug / Story）

### 去重检查（必须）
创建前，先查询当前项目未关闭的同类 Ticket，对比标题和描述是否有相似的。
- Bug: 用 `get_bug` 查询
- Story: 用 `get_stories` 查询
- 如果发现疑似重复，列出相似的 Ticket（标题、状态、处理人、链接），问用户："这几个看起来相关，还要新建吗？"
- 用户确认后再创建

### 图片附件（必须）

消息里带图，或者请求里出现**「如图」「见图」「截图里」「规则如图」**这类指代——
两种情况都必须把图附到票上。

**图片和请求经常不在同一条消息里。** 真实的发法通常是：先发一张截图，
过一会儿再 @ 机器人说「按这个建个票」。这两条会落在不同的批次里，
**当前这条消息的上下文里没有 MediaPath**。

所以：请求里只要出现「如图」这类指代，就**往上翻最近的对话**，
找那条带 `MediaPath` 的消息，把路径取出来。找不到就明确问用户
「你说的图是哪一张」，不要默默建一个没有图的票——
描述里写着「规则如图」却没有图，读的人只会更困惑。

把 `MediaPath` 的**本机绝对路径原样**传给 `image_url`（单张）或 `image_urls`（多张，数组）。
MCP 会自动上传到 TAPD 图床并内嵌进描述，不需要外部图床，也不需要你先做上传这一步。
多张要全传，不要只挑一张。

单张限 5MB。上传失败工具会直接报错，如实转达失败原因——
不要静默跳过附件，更不要谎称已附上。

### 迭代关联（必须）

**默认放进「今天所在的那个迭代」，不是最新的迭代。**

用 `get_iterations` 拿到列表，然后按 `startdate <= 今天 <= enddate` 选，
只有恰好包含今天的那一个才是答案。

先确认今天是几号（`date '+%F'`），别用记忆里的日期。

这三种情况**一律问用户，不要自己挑**：

- 今天不落在任何迭代区间内（迭代还没排到今天，或中间有空档）
- 有多个迭代同时包含今天
- 用户在需求里明确说了迭代 —— 那就按用户说的，不要再去推断

**「取最新的那个」是错的写法，别这么理解。** 未来的迭代通常也是 `open`、
结束日期也没过，按"最新"会选到几周之后的迭代——票就飘到未来的 sprint 里，
不会出现在当前迭代的看板上，没人看得见。

举例：今天 08-26，SPRINT 3 是 08-24~08-30、SPRINT 6 是 09-14~09-20，
两个都 open、都没结束——**答案是 SPRINT 3**。

### 必填字段
- title / name（标题）
- description（描述）

### 可选字段
- current_owner / owner（处理人）— 如果上下文有明确的负责人
- priority_label（优先级）— 如果用户明确提到

### 描述写法（必须）

description 支持 **Markdown**，MCP 会自动渲染成 HTML 再写进 TAPD。实测标题、表格、引用块、代码块、加粗、分割线、链接**全部有效，TAPD 不做任何清洗**。

不要把整张票写成一片「背景：… 当前现象：… 跟进目标：1. 2. 3.」的散文 —— 渲染出来只有一堆密排段落，别人打开抓不到重点。

**小标题一律用 `####`（四级）。** TAPD 的富文本样式里 `##` 会渲染得比票标题本身还大，`###` 也偏大，只有 `####` 跟正文比例才合适。

按下面这个骨架写，**没内容的小节直接删掉**，不用凑齐：

````markdown
#### 背景

一两句交代上下文和正确口径。接口路径、参数、字段名一律用 `反引号`。

#### 现象

| 字段 | 期望 | 实际 |
| --- | --- | --- |
| `localAttributes` | 有 node | 缺失 |
| `price` | CNY_CHN | 未返回 |

影响面一句话说清。

#### 外部确认

> 引用块专门放「别人说的」—— 对方团队的结论、群里的原话、外部工单状态。

#### 跟进目标

1. 谁 负责 做什么
2. 怎么验证
3. 什么条件下归因到哪一侧

#### 补充记录

- **2026-08-21** 后续补充记在这里，日期加粗

---

— [AI Bot]
````

**两个 Markdown 陷阱，务必避开：**

- **嵌套列表要缩进 4 个空格。** 用 2 个空格会被拍平成同级，层次全丢。
- **无序列表后面紧跟有序列表，会被合并成一个无序列表。** 两种列表之间必须隔一个小标题或分割线，否则你写的 `1. 2. 3.` 会渲染成圆点。

其他约定：

- 小标题只用 `####`，不要用 `#` / `##` / `###`
- 字段名 / 接口 / 参数 / 错误码 / 文件路径一律用反引号包起来
- 长 JSON、报文、日志用围栏代码块（三个反引号），会渲染成等宽块，但没有语法配色
- 内容很少的票不必套满骨架，两个小标题也远好过一片散文
- 结尾的 `— [AI Bot]` 签名按上面「[AI Bot] 签名」一节的规则照常加


### 创建完成后的输出格式
只展示以下信息，不要展示 ID：
- 标题
- 迭代名称
- 处理人
- TAPD 链接
  - Bug: `https://www.tapd.cn/{workspace_id}/bugtrace/bugs/view/{bug_id}`
  - Story: `https://www.tapd.cn/{workspace_id}/prong/stories/view/{story_id}`

## 更新 Ticket

### 行动原则
用户说"修好了"→ 直接查工作流 → 直接流转状态 → 直接补评论 → 返回结果。整个过程一气呵成，中间不要问任何确认。
不要问"要不要更新"、不要问"要更新到哪个状态"、不要问"要不要补评论"。这些全部自动完成。

### 状态流转规则

#### Bug Happy Path

new(新) → in_progress(接受/处理) → resolved(已解决) → verified(已验证) → closed(已关闭)

其他常见流转：
- 任何状态 → rejected(已拒绝)：拒绝 bug
- rejected → closed(已关闭)：关闭已拒绝的 bug
- closed/rejected/resolved → reopened(重新打开)：重新打开

使用 `v_status` 传中文名，如 `v_status: "已关闭"`。

#### Story/需求 Happy Path

planning(规划中) → developing(开发中) → status_3(测试中) → resolved(已实现) → end

其他常见流转：
- planning/developing → rejected(已拒绝)：拒绝需求
- rejected → planning(规划中)：重新规划
- rejected/resolved → end：归档结束

使用 `v_status` 传中文名，如 `v_status: "开发中"`。注意：测试中对应 `v_status: "测试中"`，归档对应 `status: "end"`（无中文别名时用英文 key）。

#### 遇到问题时

如果 `v_status` 更新失败（状态名不匹配或当前状态不允许该流转）：
1. 调 `get_workflows_all_transitions` 查当前可用的流转路径（返回英文 key）
2. 用 `status` 字段传英文 key 重试（如 `status: "closed"`）
3. 如果仍然失败，列出可用的目标状态让用户选择

### 评论规则（状态变更时自动执行，不要询问）
任何状态变更都必须同时用 `create_comments` 添加评论，不要单独询问用户是否需要评论。
评论内容：
- 以 "[AI Bot]" 开头，标明来源
- 整理对话中与该 Ticket 相关的讨论，提炼关键信息
- 例如："[AI Bot] Cindy反馈已修复首页移动端加载性能问题，请验证。"

### 变更处理人
- Bug: 用 `update_bug` 修改 `current_owner`
- Story: 用 `update_story_or_task` 修改 `owner`
- 如果用户没指定人，用分配规则推荐

## 分配 Ticket

- 结合 Ticket 的历史处理人、对话上下文、memory 中记住的团队分工推荐
- 给出推荐人选和理由，让用户确认
- 如果用户指定的人在 contact_map 中找不到，不要继续，必须先追问用户确认此人的企业微信中文姓名

## 删除 Ticket

### 二次确认（必须）
删除前必须明确告知用户即将删除的 Ticket 标题，等用户明确确认后才执行。
