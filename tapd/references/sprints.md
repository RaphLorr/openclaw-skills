# Sprint / 迭代管理

适用于创建、查询、修改 Sprint，以及建票时选择/补建迭代。Sprint 在 TAPD 工具中叫 iteration。

## 项目、人员和日期

- 从本群已绑定的 TAPD workspace 或用户明确指定的项目解析 `workspace_id`；不明确时先询问，不跨项目创建。
- 用当前时间和项目时区解析“本周/下周”等相对时间；未配置项目时区时使用当前会话时区（本部署通常 Asia/Shanghai）。不要使用旧对话中的日期。
- 用户指定迭代名称优先；否则按用户给出的工作计划日期选，无计划日期才按今天选。
- 默认周期是一周：目标日期所在周的周一到周日，起止日期都包含。只在用户没有其他周期要求时建议这个周期；两周/自定义日期按用户明确要求执行。不要把工作日截止日当成迭代的结束日期。
- 周区间用日期运算：周一起始 = 目标日期减 `weekday()` 天（周一=0），周日 = 周一加 6 天。跨月跨年照常计算，不用“今天加 7 天”推算下周一。
- `creator` / `current_user` 按主 skill 的人员规则解析；工具可能由授权账号覆盖这些字段。不要凭空猜姓名，也不要声称实际创建人一定是请求者。

## 查询和去重

调用 `get_iterations(workspace_id, options)`，读取 `id/name/startdate/enddate/status`，按接口支持的分页查全相关结果。不要仅取最新一页，也不要把查询失败、权限错误或响应无法解析当成“没有迭代”。

- 明确的迭代名称有唯一匹配时使用它；不存在则给出建议名称/日期，询问是否创建。
- 自动选择时，检查目标工作日期/完整计划区间是否被唯一可用迭代包含；不是只检查截止日。默认不选择已关闭迭代。
- 多个包含、部分重叠、计划跨越多个迭代、或仅发现覆盖目标的已关闭迭代：列出具体名称和日期，请用户选择如何归属；不要自动新建重叠迭代或重新开启旧迭代。
- 无匹配也无冲突时才提出创建方案。检查名称和日期是否重复，包括已有的关闭迭代。
- 建议名称沿用该项目清晰且唯一的命名惯例；例如最近为 SPRINT-1 且序号可确认时建议 SPRINT-2。不确定时用日期型名称（如“2026-10-26 至 2026-11-01”）并放入确认问题，不能冒充项目已有命名规则。

## 先确认，再执行

只要求建票不代表授权额外创建迭代。没有匹配时，先保留票的标题、描述、处理人、附件、计划日期等信息，发出一次合并确认：

> 下周还没有对应迭代。要新建「SPRINT-2」（10/26 周一—11/01 周日），再为你和 Jerry 建这张票吗？我默认按周一到周日的一周安排，需要其他周期也可以告诉我。

名称仅作示例，以查询到的项目情况为准。此时不要提前创建未归属或误归属本周的票，不要承诺已创建。无回复、闲聊、单纯提及其他人都不能视为同意。若用户只确认新建迭代而未请求建票，则仅新建迭代。

用户回复“可以/就这样”且明确指向这个待确认方案后，无需再次询问。执行前重新读取对话，合并期间的名称、日期、周期调整，并确认工作区相同；再查询一次迭代和同类 ticket，防止等待期间其他人已创建。

用户拒绝新建时，询问使用哪个已有迭代或是否明确允许不挂迭代；不能静默挂到本周。用户改变计划或项目时，旧的确认不适用于新的范围。

## 创建及验证

`create_iteration(workspace_id, options)` 的关键字段：

```json
{
  "name": "用户确认的名称",
  "startdate": "2026-10-26",
  "enddate": "2026-11-01",
  "creator": "按人员映射解析的姓名",
  "status": "open",
  "description": "本次迭代目标\n\n— [AI Bot]"
}
```

上面的日期仅为示例，不能照搬。开始日期不得晚于结束日期；只有用户明确需要时才设置 `parent_id` 或标签，不能猜父迭代。

1. 如复查发现相同迭代已经存在，使用现有 ID，不重复创建。遇到新出现的冲突时先询问。
2. 调用创建工具后检查业务成功状态和 `Iteration.id`，必要时用 `get_iterations` 按返回 ID 核实名称/日期；不能只凭外层工具调用未抛异常就判断成功。
3. 若还有先前已授权的建票请求，调用对应建票工具，传入刚验证的 `iteration_id`，保留原票信息，继续遵守去重、人员、附件和签名规则。
4. 创建结果/网络响应不明确时先查询，不盲目重试；只有确认没有创建成功且授权仍有效时才重试。

## 部分成功与修改

- 迭代成功、ticket 失败：明确返回“迭代已创建，建票未成功”及迭代链接。后续只补建 ticket，不重复创建迭代，也不自动删除迭代。
- 迭代创建失败或未确认成功：暂停建票并说明原因，不改挂其他迭代。
- ticket 成功但附件/预览失败：报告对应附件结果，不再次创建迭代或 ticket。
- 修改迭代使用 `update_iteration`，先查询确定 ID，只传用户要求变更的字段；不要因“下周没迭代”而挪动、延长或重开旧迭代。仅修改描述时保留原文并追加签名。

## 完成回复

迭代名称、实际起止日期、迭代链接；若同时建票，再给出票标题、处理人、ticket 链接。只确认真实成功部分，原始数字 ID 留在工具调用中。迭代链接优先使用工具返回的 `url`。
