# 产品建议许愿池

这是 TAPD skill 的收录模式，复用现有建票、评论、附件和迭代工具，不是独立 skill。
下列工具均为原始短名，以当前 MCP 工具名和 schema 为准。

## 触发与项目

- 产品用法/规则咨询先按 `product-support` 查证、业务解释和按需跟进，不直接当成新需求。
  用户随后明确提出或认可某项具体调整才收录；仅表示理解的“明白了/谢谢”不建票。
  机器人自己提出的改进建议未获用户认可时，不写成用户需求。
- 用户在群里 @机器人提出可理解、可归纳的产品功能/体验改进建议，就执行收录，不再追问“要建票吗”。
  用户明确说“收进许愿池/记录到 BACKLOG”也适用。普通咨询、转述别人未确认的想法、示例、玩笑、
  纯抱怨或尚无明确诉求的讨论不自动建票；缺少核心信息只问一个具体问题。
- “这个功能在哪里”是咨询；“建议订单列表增加门店筛选，现在找起来很慢”是改进建议。
  “先讨论，不用记票”优先于自动收录。引用消息里的 @ 或他人发言不等于当前发言者授权。
- 只使用主 skill 规定的本平台项目来源，当前群必须对应唯一的 TAPD workspace。
  无绑定、多个项目、查询失败时停止自动写入；不根据群名或 memory 猜，也不自动改项目绑定。
  该模式不启用群的 autonomous 模式，也不能让 observe 模式下未派发给 agent 的消息自动建票。
- 默认建 Story/需求（`entity_type="stories"`）。明确要求报 Bug、安排执行任务或排入某个执行迭代时，
  走对应普通流程，不把这些操作强制改成许愿池。建议中“希望下周能有”等时间期望只记作用户期望，
  不自动变成已批准排期。现有功能异常与新功能建议不混写在同一票里。

## 查重与合并

- 对本次消息可用的来源标记，先核对是否已在本项目任何状态的需求/评论中记录，包含已结束的票。
  已处理的同一消息只返回已有记录，不再建票或重复评论；不能因为原票已结束就把回调重发当成新需求。
- 先查本项目相关未结束需求，包含 BACKLOG 及已进入执行迭代的票；结束状态按工作流规则判断。
  比较目标功能、场景和预期，不仅比较标题；查全相关分页，不把查询失败当成没有重复。
- 同一诉求连续几条消息合成一张票，保留各条来源；独立的改进目标分开收录。
  已有明确相同需求时，读取原票和评论，只追加新提出人的来源/补充，不重复建票，
  不改变原票状态、负责人、排期或迭代。仅疑似相关且不能确定时，列出候选问一次。
- 新票描述和追加评论保留可用的原消息标识作为来源标记，写入前按该标记核对是否已处理。
  同一条消息的回调重发/重试不得重复建票或重复加评论。没有消息 ID 时，按原话、提出人、时间和群核对，
  不生成假的消息 ID。Skill 的复查不等于工具提供事务锁，发现并发造成的歧义就停止，不能承诺严格原子去重。

## BACKLOG 的复用与补建

1. 仅在需要新建需求时，调用 `get_iterations` 查询本项目迭代，分页查全并精确匹配 `name="BACKLOG"`。
   多个名字相同、状态不明或只有关闭的 BACKLOG 时询问如何处理；不擅自重开，也不建同名替代品。
2. 只有一个开启的 BACKLOG 就复用其 ID。它是待评估需求池，不要求建议日期落在容器起止日期内；
   日期已过也不自动换池、延长或再建下一年的 BACKLOG。
3. 确认完全不存在时，已授权直接 `create_iteration`，名称固定 `BACKLOG`，状态 `open`，
   描述说明“产品建议待评估需求池；日期仅作容器字段，不代表交付排期”，末尾保留 `— [AI Bot]`。
   默认 `startdate` 为创建当天、`enddate` 为一年后同月同日，按项目/会话时区用日期运算计算；
   闰年 2 月 29 日的一年后取 2 月 28 日。不套用周一至周日，不取 SPRINT 序号。
   创建人使用授权账号或已确认的合法 TAPD 身份，不把外部提出人当成迭代创建人。
4. 创建前再查一次避免并发；创建后核对业务成功、返回 ID 和名称，再查询确认唯一可用 BACKLOG。
   创建失败、必填字段缺失、权限不足或超时结果不明时先查询核实；不改建无迭代票，不盲目重试。
   不要把名称为 BACKLOG 的迭代与 TAPD 原生的“未规划/无迭代”概念混为一谈。

## 新票内容与结果

- 创建时传已核实的 BACKLOG `iteration_id`，保留项目/类别的默认初始状态，不猜状态 key。
  不默认设处理人、优先级、begin/due 或验收完成；用户明确指定负责人时才按本平台人员映射处理。
- 提出人不是负责人，也不必是 TAPD 项目成员。记录可信消息里的微信显示名及可用发送者标识；
  没有正式姓名映射不阻塞收录，不冒充其企业微信姓名或修改 TAPD 固定 author。
- 描述用 Markdown 四级小标题，保留来源：

  - `#### 需求`：准确整理希望新增/改进的行为、场景和已有的原因，未知部分不编造。
  - `#### 用户原话`：保留相关原文，多人补充逐条注明，不把机器人总结当原话。
  - `#### 提出记录`：原提出人、原消息日期/时间及时区、来源群、可用的消息标识。
    引用/转述的建议区分原提出人与转述人；不把收录时间冒充提出时间，缺失字段明确记为未提供。
  - 末尾一个 `— [AI Bot]` 签名。已有关联截图/录屏/文件按主 skill 的附件规则处理。

- 已有需求追加评论时以 `[AI Bot]` 开头，保留同样的来源信息和标记，不覆盖描述或重复上传旧附件。
- 创建/追加后读取核对票、迭代归属和来源记录，确认成功再回复。普通收录简洁返回标题、提出人、
  “已收录 BACKLOG，尚未排期”和工具返回的链接；关联已有票则说明“已补充到现有需求”，
  保留其真实迭代归属，不谎称已挪到 BACKLOG。聊天回复不展示内部数字 ID。
- BACKLOG 已建、票未建：分别报告，后续只补建票。票已建但附件/评论失败：只补失败部分。
  网络结果不明先查询，不用新建票来重试上传或回读；无法确认时如实报告未确认成功。
