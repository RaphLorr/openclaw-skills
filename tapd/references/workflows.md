# 项目工作流与状态

以下使用 MCP 工具的原始短名；调用时以当前连接实际的名称和 schema 为准。
缺少工具时先发现工具或报告连接问题，不绕过 MCP 写原始 API。

## 查询范围

- 单票操作先确定目标链接/ID 和本次项目，读取原票，取得 `status`、`workspace_id`；
  Story/feature/需求还要读取 `workitem_type_id`。不能把对话里的“任务”一律当成 Task，
  实体类型以票据为准。类别缺失时先补查，不用项目所有类别的混合状态猜测。
- Story 使用 `system="story"`，并始终带上本票的 `workitem_type_id`；
  Bug 使用 `system="bug"`。每次状态写入都查询当前配置，不沿用其他项目、类别或旧对话的状态表。
- 用同一范围查询：`get_workflows_status_map` 获取合法状态 key 与显示名；
  `get_workflows_last_steps` 获取配置的结束状态；
  `get_workflows_all_transitions` 获取当前状态的直接路径和附加必填字段。
  Task 不使用这三项 Story/Bug 工作流查询，按任务接口的实际状态规则处理。
- 结束状态可能不止一个；筛选未关闭票时，应排除该范围配置的全部结束状态，
  不能假设只有 `closed`，或用标题中的“关闭/结束”猜是否已结束。
  需求列表涉及多个类别时，先取得实际类别并分别查询结束状态，再按类别筛选。

## 选择目标

- 写入目标必须存在于 `status_map`。流转表中的 `start`、`end` 可能是流程边界节点，
  仅有一条指向它们的边不代表能写入；如果项目确实将同名 key 配置为业务状态，才按该配置处理。
- “已处理完成”选择符合完成含义的状态，不能选成“已拒绝/取消”，也不能凭空声称已测试、验证或验收。
  “关闭”结合 `last_steps` 和具体业务含义判断；不能仅因某个状态是结束状态就自动选择它。
- 同时满足合法状态、用户意图/事实和当前直接路径的目标唯一时，直接执行。
  多个目标仍合理时列出候选并询问一次；没有直接路径或缺少验证依据时说明阻碍，
  不自动连走多个中间状态、伪造验证或跳过必填字段。不要为此改项目工作流。
- 已在符合用户意图的结束状态时，报告已结束；有新的完成反馈可补一条事实评论，
  不为“再关闭一次”改成其他结束状态或重复同一评论。

## 写入、回读与失败

- 使用确认过的英文 `status` key。若使用 `v_status`，须与当前范围中唯一的显示名一致；
  不同时发送冲突的两个字段。需求类别变更与状态变更分开处理。
- 更新后回读原票，确认实际状态匹配目标，再报告成功并补一次 `[AI Bot]` 评论。
  评论只记录用户反馈及已确认结果，不冒充独立测试；评论失败不重做状态更新。
- MCP 返回 `workflow_validation_failed` / `updated=false` 时，说明未写入；根据返回的
  `valid_statuses`、`terminal_statuses`、`next_statuses` 核对，再重新查询当前范围。
  只有确认了新的合法目标和路径才尝试一次修正；再次被拒绝或仍有歧义就停止并说明阻碍。
  不把中文状态失败当成可以猜英文 `end` / `closed` 重试的理由。
- 超时或结果不明时先回读核实，不能假定没写入而盲目重试。
  如果原票已处于映射中不存在的状态，报告需要单独修复，不通过普通状态流转、
  另一写入入口或原始 API 绕过 MCP 校验。工作流查询失败或配置不一致时不写状态。
